# Gemma 4 E4B 페르소나 LoRA — VRAM 절약·빠른 학습 조사 (2026-10-14)

## 결론
- **학습 베이스 = `google/gemma-4-E4B-it-qat-q4_0-unquantized`** (Google 공식 QAT 가중치, BF16, 15.9 GB, Apache-2.0)
- **배포 베이스 = 같은 가중치의 GGUF**
  - 기본: `google/gemma-4-E4B-it-qat-q4_0-gguf` → `gemma-4-E4B_q4_0-it.gguf` **5.15 GB** (공식)
  - 저사양: `unsloth/gemma-4-E4B-it-qat-GGUF` → `UD-Q2_K_XL` **3.22 GB** (같은 QAT 가중치, 2비트급)
  - → LoRA 하나로 두 파일 모두에 맞음. 일반 E4B로 학습하고 QAT GGUF에 얹으면 가중치가 달라 미세하게 어긋나므로 QAT 원본으로 학습하는 게 정답.
- **방법 = 자체 QLoRA 스크립트** (`training/train_persona_lora.py`). 네라 손 LoRA 때 E4B에서 이미 검증한 파이프라인을 페르소나용으로 개조.
- 원본(무검열 아님) 모델 사용 → 부적절한 요청은 원래 모델처럼 자연스럽게 피해 감. 단 **파인튜닝은 이 회피 성향을 약하게 만들 수 있으므로** 학습 데이터에 자연스러운 회피 예시를 넣고, 학습 전/후 같은 질문 30개로 비교 검사한다.

## E4B 구조에서 메모리가 어디 쓰이나 (config 실측)
| 부분 | 크기 | 처리 |
|---|---|---|
| 언어 층 42개 (hidden 2560, MLP 10240) | ~3.7B | NF4 → 약 2.2 GB |
| 토큰 임베딩 = lm_head (어휘 262,144) | 0.67B | bf16 1.3 GB (공유 가중치, 양자화 안 함) |
| **층별 임베딩(PLE) 표 262144×42×256** | **2.8B = 5.6 GB** | GPU에 안 올림. 파일에서 필요한 행만 mmap 조회 |
| 비전·오디오 타워 | ~0.9B | 제거 |
| 마지막 18층은 KV를 앞 층에서 공유 | — | 이 층들엔 k/v 투영이 없음 → LoRA는 q/o + MLP만 |

## 기법별 효과 (우선순위 순)
1. **PLE mmap 조회** — 5.6 GB 절약. Unsloth 문서에도 PLE 처리법은 없음 (우리 방식이 더 가벼움).
2. **NF4 QLoRA** — Unsloth 공식: E4B LoRA(bf16) 17 GB, QLoRA 10 GB. 우리는 PLE·타워 제거로 그보다 낮게 예상(로드 후 ~3.7 GB). Unsloth도 "E2B LoRA보다 E4B QLoRA가 낫다"고 권장.
3. **lm_head를 정답 위치에서만 계산** — 어휘 262k라 로짓이 가장 큰 활성 메모리. bs4×1024토큰이면 전체 로짓 fp32 4.3 GB → 정답(말포이 대사) 위치만 계산해 절반 이하로. transformers `logits_to_keep`에 위치 텐서 전달로 구현(커스텀 커널 불필요).
4. **손실은 말포이 턴에만, 멀티턴 전체 턴 학습** — 대화 하나에서 말포이 대사 2~3개를 한 번에 학습 → 같은 데이터로 2~3배 신호.
5. **길이 버킷 + 64 배수 패딩** — 패딩 낭비 최소, Triton 재컴파일 방지(이전 학습에서 189분→20분 단축의 핵심).
6. **VRAM 상한(0.85)** — 넘으면 공유 메모리로 새서 RAM 100% + 10배 느려지는 문제(이전에 겪음) 차단.
7. **gradient checkpointing은 프로브 후 결정** — 데이터가 짧아(대화 2~6턴, 대부분 512토큰 이하) VRAM이 남으면 끄는 게 약 30% 빠름. `--probe`로 최장 배치 3스텝을 돌려 최대 VRAM/토큰 속도를 실측.
8. **단독 실행** — 학습 중엔 llama-server 등 GPU 서비스 정지(`supervisor.py pause all`). 다른 GPU 작업(neurovita 등)이 켜져 있으면 VRAM 상한을 낮춤.

## 하이퍼파라미터 (초기값)
- rank 16 / alpha 32 / dropout 0.05, 대상: 모든 언어 층 q·k·v·o + gate·up·down (KV 공유 층은 k·v 자동 제외)
- lr 1e-4 코사인, 유효 배치 16, 3 에폭, 에폭마다 val 측정 → **val 최저 체크포인트를 최종본으로** (페르소나 학습은 과적합되면 같은 말만 반복)
- 시스템 프롬프트는 앱이 쓰는 것과 동일한 짧은 문장 + 관계 단계(`training/system_prompt.txt`) → 학습/실사용 형식 일치
- 생각(thinking) 모드 끔. 소형 Gemma 4 템플릿은 비생각 모드에서 생각 블록이 붙지 않음(실측 확인).

## 예상 시간
600 대화 × 평균 ~350토큰 ≈ 21만 토큰/에폭. 4070 NF4 QLoRA 기준 대략 1~2천 토큰/초 → **에폭당 2~4분, 3 에폭 15분 안팎**. 데이터가 작아서 속도보다 품질 반복(데이터 고치고 다시 학습)이 병목 → 한 번 돌리는 시간을 짧게 유지하는 게 목표.

## 학습 후 배포 경로
1. PEFT 어댑터 → llama.cpp `convert_lora_to_gguf.py --base <QAT 설정 폴더>` → `malfoy-lora-v1.gguf` (수십 MB)
2. `llama-server -m gemma-4-E4B_q4_0-it.gguf --lora malfoy-lora-v1.gguf` (D:/ 경로에선 `--lora-scaled` 버그 → `--lora` 사용, 이전 실측)
   - **실측 확인(2026-10-14)**: 공식 `gemma-4-E4B_q4_0-it.gguf` + 우리 LoRA GGUF가 llama.cpp에 정상 로드, `/lora-adapters`로 실시간 on/off 가능. 생성 속도 4070 기준 LoRA 끔 93~100 tok/s / 켬 82~84 tok/s.
   - **반드시 `--jinja` + 요청마다 `chat_template_kwargs: {"enable_thinking": false}`**. 이걸 빼면 시스템 프롬프트가 있을 때 E4B가 영어로 "Here's a thinking process…"를 본문에 쏟아냄(실측). 끄면 원본 모델만으로도 말포이 말투가 나오지만 "(눈썹을 찌푸리며…)" 같은 지문을 붙임 → 지문 없는 대사체는 LoRA로 학습.
3. 설치 매니저 매니페스트에 위 GGUF 2종 + LoRA URL·크기·SHA256 등록
